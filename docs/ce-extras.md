# Расширения конфигурации Community Edition

`tnt-ce-extras` занимает в Tarantool Community Edition место модуля
`internal.config.extras`, который ядро зовёт при старте конфигурации,
и ведёт реестр расширений: каждое объявляет, какие узлы схемы с меткой
«только Enterprise» ему открыть, какой источник конфигурации
зарегистрировать и что сделать после применения.

```lua
-- app/memory.lua — модуль расширения, его называют в TNT_CE_EXTENSIONS
require('tnt.ce.extras').register('memory', {
    relax_prefixes = { 'config.etcd' }, -- принять раздел, который CE отвергает
    source = new_memory_source,         -- свой источник конфигурации
})
```

```sh
TNT_CE_EXTENSIONS=app.memory tarantool --name instance-001 --config config.yaml
```

Без переменной `TNT_CE_EXTENSIONS` пакет не делает ничего: ставить его
можно в любой образ.

## Зачем пакет

Конфигурация Tarantool 3 собирается из источников, и в Community Edition
их два: переменные окружения и файл. Схема конфигурации при этом знает
больше: `config.etcd`, `config.storage`, раздел `security` и ещё сотни
узлов помечены «только Enterprise», и CE отвергает конфигурацию с ними:

```
[cluster_config] config.etcd: This configuration parameter is available only in Tarantool Enterprise Edition
```

Свои источники Enterprise добавляет модулем `internal.config.extras`,
встроенным в бинарник. Ядро зовёт его при старте конфигурации, а в CE
такого модуля нет — и ядро в исходниках прямо разрешает подставить свой:
«Tarantool Community Edition may be extended using the same mechanism».
Пакет занимает это место и делает для расширений пять вещей:

- **Одна точка входа — много расширений.** Модуль под именем
  `internal.config.extras` у процесса один. Займи его само расширение,
  второе рядом уже не встало бы. Каркас держит точку входа и реестр:
  расширение объявляет заявку, каркас применяет все заявки в нужный
  момент загрузки.
- **Метка снимается точечно.** «Только Enterprise» снимается лишь
  с заявленных путей схемы, всё прочее ядро отвергает, как и прежде.
  Метка стоит не зря: за большинством таких узлов в CE нет кода.
  Раздел `security`, открытый целиком, не поднимет узел, даже когда
  в конфигурации о нём ни строки: умолчания раздела уходят в `box.cfg`,
  а CE таких опций не знает — `Incorrect value for option
  'password_history_length': unexpected option`. Открывать можно только
  то, исполнение чего расширение приносит само. И у открытого узла
  уходит только отказ о редакции: собственная проверка ядра остаётся.
- **Установка ничего не меняет.** Пока переменная не задана, каркас
  не грузит расширений, не трогает схему и не регистрирует источников.
- **Отказ на старте, а не тихий узел.** Расширение, которое не
  загрузилось или не создало источник, останавливает старт: узел,
  молча поднятый без обещанного источника конфигурации, хуже отказа.
- **Источник виден и после регистрации.** Ядру источник отдаётся
  безвозвратно. Каркас его помнит, рассказывает о нём зонду диагностики,
  а правило о ревизии находит узлы, которые живут не на той конфигурации:
  отставшие, поднятые на снимке и не применившие прочитанное.

Зависимости: `tnt-must` (бросок без места для отказа о списке
расширений) и `tnt-env` (окружение процесса и `.env` по общему правилу
списков).

## Как пользоваться

### Подключение: `TNT_CE_EXTENSIONS`

Пакет ставится обычным роком. rockspec кладёт модуль
`internal.config.extras` в `.rocks` рядом с остальными, и ядро находит
его обычным `require`. Расширения — модули Lua, их имена перечисляются
в переменной через запятую:

```sh
TNT_CE_EXTENSIONS=app.memory tarantool --name instance-001 --config config.yaml
```

Или строкой в `.env` каталога, из которого запускают узел:

```
TNT_CE_EXTENSIONS=app.memory
```

Список разбирается по правилу `tnt-env` для списков: режется по запятой
и только по ней, пробелы по краям имени снимаются, пустые куски
отбрасываются, пустая переменная — пустой список. Переменная окружения
процесса главнее строки в `.env`.

Пробел внутри имени — отказ. Имени модуля с пробелом не бывает,
а до перехода на `tnt-env` пробел тоже разделял список, и старый список
иначе отказал бы словами о пропавшем модуле, а не о разделителе:

```
переменная окружения TNT_CE_EXTENSIONS: в имени расширения «app.memory app.other» пробел, а разделитель — запятая
```

Весь список проверяется до первой загрузки: имя с пробелом значит, что
неверно записан весь список, и грузить до отказа его начало незачем.
Отказ бросается без места — текст уходит оператору, и приписка строки
пакета отправила бы искать причину не там.

Модули грузятся `require` в порядке списка. Незагрузившийся — отказ
с причиной:

```
расширение app.missing не загрузилось: module 'app.missing' not found: …
```

### Откуда берётся список

Список читается однажды на процесс — в инициализации конфигурации — и из
`.env` текущего каталога, то есть каталога запуска. Другого файла каркасу
не узнать: ядро зовёт его раньше, чем хоть один источник назвал
`process.work_dir`. Ни применение конфигурации, ни `config:reload()`
список не перечитывают — расширения заводятся однажды. Поэтому:

- `TNT_CE_EXTENSIONS` пишется в окружение процесса или в `.env` каталога
  запуска;
- строка в `.env` рабочего каталога (`process.work_dir`) не действует
  никогда, а не «со второго раза»: проверено на узле 3.8 — такой узел
  отвергает `config.etcd` уже на старте.

Чтение у каркаса своё (`env.new()`), а не общее на процесс: каркас зовут
до `box.cfg` и до перехода в рабочий каталог, и общее чтение, заведённое
здесь, закрепило бы за приложением `.env` каталога запуска.

`.env` каталога запуска, который есть и не читается (ошибка разбора),
останавливает старт уже здесь — даже без расширений. Это договор
`tnt-env`: приложение, читающее окружение тем же пакетом, отказало бы на
том же файле при первом применении конфигурации.

### Своё расширение: `register`

Расширение — модуль, который при загрузке регистрирует заявку:

```lua
local extras = require('tnt.ce.extras')

extras.register('memory', {
    relax_prefixes = { 'config.etcd' },

    source = function()
        return new_memory_source()
    end,

    post_apply = function(config)
        log.info('конфигурация применена: %s', config:info().status)
    end,
})

return {}
```

`register(name, spec)` принимает имя расширения и заявку. Имя — непустая
строка, одна на процесс: под ним расширение видно в `status()`
и `sources()`. Поля заявки необязательны:

| Поле | Что это | Когда в ходу |
|---|---|---|
| `relax_prefixes` | список путей схемы, с которых снять метку «только Enterprise» | при инициализации, однажды на процесс |
| `source` | фабрика источника конфигурации: функция без аргументов, отдающая таблицу источника | при инициализации; источник регистрируется у ядра |
| `post_apply` | функция `post_apply(config)` | после каждого применения: на старте и на каждом `config:reload()`, в том числе неудачном |

Заявка действует, когда сделана при загрузке модуля из списка: каркас
грузит расширения и сразу применяет все заявки реестра, в порядке
регистрации. Заявка, сделанная позже, не откроет схему и не добавит
источника — инициализация у процесса одна.

Ошибки заявки — ошибки программиста, и бросаются исключением:

```
имя расширения должно быть непустой строкой
расширение memory уже зарегистрировано
заявка расширения memory должна быть таблицей
relax_prefixes расширения memory должен быть списком строк
source расширения memory должен быть функцией-фабрикой
post_apply расширения memory должен быть функцией
```

Фабрика, отдавшая не таблицу, останавливает старт:
`расширение memory не создало источник конфигурации`.

### Источник конфигурации

Договор источника задаёт ядро. Источник — таблица с полями:

| Поле | Что это |
|---|---|
| `name` | имя источника у ядра: под ним ядро хранит сведения о нём |
| `type` | `'instance'` — конфигурация инстанса, `'cluster'` — кластера, с группами и репликасетами |
| `sync(self, config, iconfig)` | прочитать конфигурацию: ядро зовёт на старте и на каждом перечитывании; `iconfig` — собранное из источников до него |
| `get(self)` | отдать прочитанное |
| `status(self)` | необязательно: что источник скажет о себе в `status()` каркаса и зонду |

Ревизию прочитанного источник сообщает ядру сам —
`config:_meta(self.name, 'revision', N)` в `sync`. Ядро помнит её как
прочитанную (`config:info('v2').meta.last`) и переписывает применённую
(`meta.active`) только после удачного применения.

Источник, собранный в живом примере этого документа:

```lua
local function new_memory_source()
    local values = {}
    local revision = 0

    return {
        name = 'memory',
        type = 'cluster',

        sync = function(self, config)
            revision = revision + 1
            values = { app = { cfg = { greeting = 'привет' } } }
            config:_meta(self.name, 'revision', revision)
        end,

        get = function()
            return values
        end,

        status = function()
            return { stale = false, revision = revision }
        end,
    }
end
```

Узел с этим расширением и `config.etcd` в файле поднимается:

```lua
config:info().status                --> 'ready'
config:get('config.etcd.prefix')    --> '/demo'
config:get('app.cfg.greeting')      --> 'привет'
config:info('v2').meta.active       --> { memory = { revision = 1 } }
```

Порядок источников тоже задаёт ядро: окружение, файл, затем источники
расширений — в порядке регистрации, — и последним окружение
с умолчаниями (`TT_*_DEFAULT`). Значение первого источника главнее:
источник расширения не перекроет ни окружения, ни файла.

### Открыть узлы схемы: `relax_prefixes`

Путь узла — имена полей от корня схемы через точку: `config.etcd`,
`security.auth_delay`. Узел открывается, если его путь совпадает
с заявленным или начинается с заявленного и точки: `config.etcd`
открывает и `config.etcd`, и всё под ним, но не `config.etcdx`. Элементы
массива в пути — `.*`, ключи и значения словаря — `.[key]` и `.[value]`.

У открытого узла снимается метка, из его проверки уходит только отказ
о редакции, а умолчание применяется и в CE. Остальные проверки на месте.
Ключ вне схемы ядро по-прежнему отвергает («Unexpected field»).
Проверки потомков работают: `config.etcd.prefix` без ведущей косой черты
отвергается. Собственная проверка самого узла тоже: раздел `config.etcd`
без `prefix` отвергается на старте, а не всплывает ошибкой позже,
в источнике:

```
[cluster_config] config.etcd: No config.etcd.prefix provided
```

Свою проверку узла ядро сцепляет с проверкой редакции в одну функцию,
и разнять цепочку снаружи нечем. Зато обе половины отказывают одним
путём — вызовом `w.error`. Открытый узел зовёт цепочку целиком, а в `w`
глохнет ровно отказ «This configuration parameter is available only
in Tarantool Enterprise Edition»; любой другой отказ доходит до ядра
как есть. Умолчание узла заменяется целиком: проверка редакции отвечает
в нём значением, а не отказом, и заглушить её нечем, — а своего условия
умолчания у узлов с меткой на 3.8 нет.

Вывод каждого источника ядро проверяет порознь, поэтому раздел пишут
целиком в одно место. Если `endpoints` лежит в файле, а `prefix` —
в окружении (`TT_CONFIG_ETCD_PREFIX`), отказ придёт о файле, если
наоборот — об окружении:

```
[instance_config] config.etcd: No config.etcd.prefix provided
```

Открываются обе схемы — инстанса и кластера: схема кластера строит свои
копии узлов, и метка стоит на каждой.

Узлы открываются однажды на процесс: обход необратим, и повторная
инициализация схему не трогает. Сколько открыто, видно в
`status().relaxed_nodes`: для `config.etcd` на 3.8 — два, по узлу
в каждой схеме. `count_enterprise_nodes()` отвечает, сколько узлов ещё
помечено: на 3.8 без заявок — 370, 74 в схеме инстанса и 296 в схеме
кластера. Оба числа — сторож обновления Tarantool: изменились — схема
поехала, и список путей пора пересмотреть.

### Состояние: `status`, `sources`, `registered_names`

```lua
extras.status()
--> { extensions = { 'memory' }, relaxed_nodes = 2, schema_patched = true,
-->   sources = { memory = { revision = 1, stale = false } } }
```

В `sources` — то, что каждый источник сказал о себе методом `status`.
Источника без метода там нет: договор ядра рассказа о себе не требует.
Источник, чей `status` бросил, виден как `{ err = 'текст' }` — отказ
не роняет состояние каркаса.

`extras.sources()` отдаёт сами источники по именам расширений — копией
таблицы: правка у читателя не сотрёт того, что каркас помнит.
`extras.registered_names()` — имена расширений в порядке регистрации.

### Ревизия в диагностике: `publish_probe` и `publish_rule`

```lua
extras.publish_probe(probe.register) -- поле config_sources в рассказе узла
extras.publish_rule(issues)          -- правило config_revision в реестре диагностики
```

`publish_probe(register)` отдаёт зонду поле `config_sources`
(`extras.diagnosis.PROBE_FIELD`): `register(name, collector)` получает имя
поля и сборщик. Рассказ о каждом источнике сложен из двух половин:
своё источник говорит сам, ревизии — у ядра.

```lua
collector()
--> { memory = { stale = false, ready = true,
-->              revision = 4, fetched_revision = 5, status = 'check_errors',
-->              errors = { 'роли missing.role нет' } } }
```

| Поле | Откуда |
|---|---|
| своё источника | его `status()` |
| `revision` | применённая ревизия: `config:info('v2').meta.active[имя источника]` |
| `fetched_revision` | прочитанная: `meta.last[имя источника]` |
| `status` | состояние ядра: `ready`, `check_warnings`, `check_errors`, `startup_in_progress`, `reload_in_progress` |
| `errors` | тексты замечаний ядра уровня `error` — почему конфигурация не применена |

Ревизию, которую назвал сам источник, заменяет применённая: по
прочитанной узел, упавший на применении, сошёл бы за догнавшего. Ревизии
берутся под именем источника у ядра (`source.name`), а в рассказе
источник стоит под именем расширения. Отказ ядра ответить не прячется:
сборщик бросает, и зонд помечает поле ошибкой.

`publish_rule(issues)` регистрирует правило `config_revision`
(`extras.diagnosis.RULE`). Реестр пакет не берёт сам — он приходит
аргументом; договор, которого правило от него ждёт, держит
`tnt.cluster.issues` из `tnt-cluster-health`:

| Поле реестра | Что даёт |
|---|---|
| `register(name, rule)` | принимает правило `{ check, personal }` |
| `SEVERITY` | уровни находок: `WARNING`, `CRITICAL` |
| `about_instance(spec)` | находку об узле из `{ rule, name, entry, key, severity, message }` |

Правило — чистая функция снимка `{ instances = { [имя] = запись } }`,
где запись несёт `reachable`, `replicaset_name` и рассказ узла
в `extensions.config_sources`. О каждом источнике узла — не больше одной
находки, в таком порядке:

| `key` | Уровень | Когда | Текст |
|---|---|---|---|
| `snapshot` | `WARNING` | источник сказал `stale = true` | `конфигурация взята из снимка: источник etcd не отвечал при старте, и что применено — неизвестно` |
| `unapplied` | `CRITICAL` | ядро в `check_errors` либо прочитанная ревизия новее применённой, а применение не идёт | `конфигурация не применена: источник etcd, прочитана ревизия 5, действует 4, ядро в состоянии check_errors: роли missing.role нет` |
| `behind` | `CRITICAL` | применённая ревизия меньше самой свежей в кластере | `конфигурация отстала: применена ревизия 41 источника etcd, в кластере уже 42` |

Подъём на снимке — поблажка осознанная: иначе отказ хранилища
конфигурации не пускал бы кластер подняться вовсе. Но что применено на
таком узле, не знает никто, и об отставании он второй находкой
не упрекается. Узел, не применивший прочитанное, назван с причиной
из замечаний ядра, а не одним отставанием: оператору нужно знать, почему
узел не догнал. Неизвестная ревизия или состояние названы прочерком.

Норма — наибольшая применённая ревизия источника, а не мнение
большинства: ревизия растёт монотонно, и та, что больше, заведомо новее.
Ревизии разных источников не сравниваются между собой.

Правило молчит, когда судить не о чем: узел недоступен, поле зонда
не таблица или помечено ошибкой, у узла нет источников расширений —
например, конфигурация лежит файлом, и ревизии у неё нет. Находки
упорядочены по имени узла и источника: без порядка список
перетасовывался бы от обхода к обходу. Правило помечено `personal`:
находка — о том, что применено на самом узле.

Модуль правила доступен и отдельно: `extras.diagnosis` —
`rule(issues)`, `describe(name, own, info)` для одного источника
и имена `RULE`, `PROBE_FIELD`, `SNAPSHOT`, `UNAPPLIED`, `BEHIND`.

### Подмена в проверках

Настоящие схемы трогать в проверках нельзя: открытие необратимо
и действует на весь процесс. Для проверок у каркаса три вызова:

```lua
extras._set_schema_provider(function()
    return { fake_schema }                  -- вместо схем инстанса и кластера
end)
extras._set_edition_provider(function()
    return 'Tarantool Enterprise'           -- вместо require('tarantool').package
end)
extras._reset()                             -- реестр, источники, отметки и подмены — в исходное
```

`_reset` открытых узлов не закрывает: обход необратим. Окружение
подменяется у `tnt-env` (`_set_source`): каркас берёт `tnt.env` через
`require` при загрузке, поэтому подменённый модуль грузится раньше
каркаса.

## Чем пришлось поступиться

**Только Community Edition.** В Enterprise модуль
`internal.config.extras` встроен в бинарник, и подмена отключила бы
штатные источники. Поэтому точка входа проверяет редакцию при загрузке
и отказывает: `пакет tnt-ce-extras предназначен только для Community
Edition: в Enterprise модуль internal.config.extras встроен в бинарник`.

**Договор ядра — внутренний.** `internal.config.extras`,
`config:_register_source`, `config:_meta`, схемы
`internal.config.instance_config` и `internal.config.cluster_config`,
сама метка `enterprise_edition` и текст отказа о редакции, по которому
открытый узел его узнаёт, — внутренности Tarantool, и между версиями
они вправе меняться. Опора здесь — проверки на 3.8: договор точки входа
(таблица с `initialize` и `post_apply`), подсчёт помеченных узлов
на настоящих схемах, открытие копии настоящего узла `config.etcd` — своя
проверка ядра обязана остаться, а отказ о редакции уйти, — и сторож
границы: в CE нет кода раздела `security`. Если он однажды появится,
сторож упадёт, и решение придётся пересмотреть. Сменит ядро текст
отказа о редакции — открытый узел снова отвергнется словами о ней:
громко, на старте, а не молча.

**Открытие схемы необратимо и общее на процесс.** Заявка открывает узлы
для всего процесса до его конца, и отозвать её нечем. Поэтому
открывается ровно заявленное, а не разделы целиком.

**Источник расширения слабее файла.** Порядок источников задаёт ядро:
окружение и файл главнее. Расширение не перекроет значения из файла —
переопределять надо там, где оно задано.

**Список расширений — однажды и из каталога запуска.** Расширения
заводятся при инициализации, а она у процесса одна; `.env` рабочего
каталога ей недоступен. Сменить список — перезапустить узел.

**Негодный `.env` роняет старт даже без расширений.** Каркас читает
`.env` каталога запуска раньше всего приложения, и ошибка разбора
останавливает старт уже здесь.

**Пробел — не разделитель.** Список со старым разделителем больше
не принимается и останавливает старт со словами о разделителе. Правило
списков одно на всё окружение, и отдельного правила для одной переменной
пакет не держит.

**Отказы — исключения, не пары.** Каркас работает на старте, и его
отказ значит «не подниматься»: пару `nil, err` ядру вернуть некуда.
Ошибки заявки — ошибки программиста, их видно при первом же запуске.

**Ревизия есть не у всякой конфигурации.** Конфигурации из файла ядро
номера не выдаёт, и правило о ревизии на таком кластере молчит. Там,
где ревизии нет, «применено разное» видно только сравнением отпечатков
применённой конфигурации, а «применено старое» без хранилища и не
случается: файл читается при старте и при перечитывании.

## Проверки

Проверки лежат в `test/` и идут на luatest. Настоящие схемы
не трогаются: источник схем подменяется поддельным деревом со всеми
формами узлов — записями, массивами и словарями, — где своя проверка
узла сцеплена с проверкой редакции, как у ядра. Открытие проверяется
и на настоящей цепочке ядра: схемный объект ядра
(`experimental.config.utils.schema`) строит копию узла `config.etcd`
со всей его проверкой, и открывается копия. Окружение и `.env` —
подмена `tnt-env`, в которой задано ровно то, что нужно проверке.
Правило о ревизии проверяется против настоящего реестра диагностики
`tnt.cluster.issues` из `tnt-cluster-health`: двойник разошёлся бы
с договором молча. Пакету реестр не нужен, поэтому зависимостью он
не объявлен и ставится только для проверок. Точка входа проверяется
на договоре ядра и на передаче обоих вызовов реестру, отказ
на Enterprise — подменой редакции.

Покрытие строк — 100 %, убитых мутантов — 100 %.

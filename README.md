# tnt-ce-extras

Расширения конфигурации для Tarantool Community Edition. Пакет занимает
место модуля `internal.config.extras`, который ядро зовёт при старте
конфигурации, и ведёт реестр расширений: каждое открывает нужные ему
узлы схемы с меткой «только Enterprise» и регистрирует свой источник
конфигурации.

```lua
-- app/memory.lua — модуль расширения, его называют в TNT_CE_EXTENSIONS
require('tnt.ce.extras').register('memory', {
    relax_prefixes = { 'config.etcd' }, -- принять раздел, который CE отвергает
    source = new_memory_source,         -- свой источник конфигурации
})
```

```sh
TNT_CE_EXTENSIONS=app.memory tarantool --name instance-001 --config config.yaml
```

Зависит от `tnt-must` (бросок без места для отказа о списке расширений)
и `tnt-env` (окружение процесса и `.env` по общему правилу списков).
Реестр диагностики приходит аргументом `publish_rule` — например,
`tnt.cluster.issues` из `tnt-cluster-health`.

## Зачем

В Community Edition у конфигурации два источника — окружение и файл,
а `config.etcd`, `config.storage` и сотни других узлов схемы помечены
«только Enterprise» и отвергаются. Свои источники Enterprise добавляет
модулем `internal.config.extras`; в CE его нет, и ядро прямо разрешает
подставить свой.

- **Одна точка входа — много расширений.** Модуль у процесса один,
  поэтому его держит каркас, а расширения подают ему заявки.
- **Метка снимается точечно.** Открываются только заявленные пути,
  всё прочее ядро отвергает, как и прежде: за большинством таких узлов
  в CE нет кода, и открытое целиком приняли бы, но не выполнили.
  У открытого узла уходит только отказ о редакции — собственная
  проверка ядра остаётся: `config.etcd` без `prefix` отвергается.
- **Установка ничего не меняет.** Без `TNT_CE_EXTENSIONS` каркас
  не грузит расширений и не трогает схему.
- **Отказ на старте, а не тихий узел.** Незагрузившееся расширение,
  пробел внутри имени в списке, источник, который не создался, —
  остановка старта со словами о причине.
- **Ревизия в диагностике.** Узел рассказывает зонду, какую ревизию
  прочитал и какую применил, а правило `config_revision` находит
  отставших, поднятых на снимке и не применивших прочитанное.

Только для Community Edition: в Enterprise точка входа отказывается
загружаться.

## Установка

```sh
tt rocks install tnt-ce-extras --server=https://tnt-skein.github.io/rocks
```

Или из исходников:

```sh
git clone https://github.com/tnt-skein/tnt-ce-extras.git
cd tnt-ce-extras && tt rocks make --server=https://tnt-skein.github.io/rocks
```

## Как пользоваться

Расширения — модули Lua, их имена перечисляются в `TNT_CE_EXTENSIONS`
через запятую, в окружении процесса или в `.env` каталога запуска.
Список читается однажды на процесс, при инициализации конфигурации.

| Вызов | Что делает |
|---|---|
| `register(name, spec)` | заявка расширения: `relax_prefixes`, `source`, `post_apply` |
| `status()` | расширения, сколько узлов схемы открыто, что источники сказали о себе |
| `sources()`, `registered_names()` | источники по именам расширений и имена в порядке регистрации |
| `publish_probe(register)` | поле `config_sources` в рассказе узла: ревизии прочитанная и применённая, состояние ядра, отказы |
| `publish_rule(issues)` | правило `config_revision` в реестре диагностики |
| `count_enterprise_nodes()` | сколько узлов схемы ещё помечено «только Enterprise» |
| `diagnosis` | правило отдельно: `rule(issues)`, `describe(name, own, info)` |
| `_set_schema_provider`, `_set_edition_provider`, `_reset` | подмены для проверок |

Источник конфигурации — таблица по договору ядра: `name`, `type`
(`'instance'` или `'cluster'`), `sync(self, config, iconfig)`,
`get(self)` и необязательный `status(self)`. Ревизию источник сообщает
ядру сам: `config:_meta(self.name, 'revision', N)`.

```lua
extras.status()
--> { extensions = { 'memory' }, relaxed_nodes = 2, schema_patched = true,
-->   sources = { memory = { revision = 1, stale = false } } }
```

Порядок источников задаёт ядро: окружение, файл, источники расширений,
окружение с умолчаниями. Источник расширения не перекроет файла.

## Проверки

```sh
make deps          # luatest, luacheck, luacov с cluacov, зависимости пакета и tnt-cluster-health в .rocks
make check         # форматирование, линт, проверки, покрытие с порогом 100 %
make mutants-all   # мутационное тестирование утилитой tnt-mutants из PATH, порог 100 % убитых
```

Покрытие строк — 100 %, убитых мутантов — 100 % (84 проверки,
175 мутантов в двух модулях; в точке входа мутировать нечего).
Настоящие схемы в проверках не трогаются: источник схем подменяется
поддельным деревом, окружение — подменой `tnt-env`. Открытие узла
проверяется и на настоящей цепочке ядра — на копии узла `config.etcd`,
которую строит схемный объект ядра. Правило о ревизии
проверяется против настоящего реестра диагностики `tnt.cluster.issues`
из `tnt-cluster-health`, точка входа — на договоре ядра.
